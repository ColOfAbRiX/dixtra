object ArrowSpacingNormalizer

Token-aware => spacing normalisation.

Token-aware => spacing normalisation.

Ensures exactly one space on each side of every => (Token.RightArrow), so Int=>String becomes Int => String. It applies uniformly to function types, lambdas, case clauses, and by-name parameters. Because it operates on RightArrow tokens, occurrences of => inside string literals or comments are single string/comment tokens and are therefore left untouched.

A space is never inserted before a line break (so a lambda whose body starts on the next line keeps no trailing space after =>). This pass assumes redundant whitespace has already been collapsed, so at most one space is ever present on either side before it runs.

If the text cannot be tokenised (should not happen after rendering), the input is returned unchanged (safety net).

object BlankLineNormalizer

Blank-line normalisation.

Blank-line normalisation.

Collapses runs of two or more consecutive blank lines (empty or whitespace-only) into a single blank line, preserving all non-blank content and the file's final newline shape.

The pass is token-aware: blank lines that lie inside a multi-line token (a """ string, an interpolation part, or a block comment) are part of that token's content and are never removed. If the text cannot be tokenised, the input is returned unchanged (safety net).

object BraceStyleNormalizer

Brace indentation style normalisation (braces.style).

Brace indentation style normalisation (braces.style).

The renderers write braces in the 1TBS style; this pass moves the braces of the whole file to the configured style:

  • 1tbs: an opening { on its own line joins the line before it, and a continuation keyword (else, catch, finally, yield) starting the line after a closing } joins that line (} else {), when the joined line fits.
  • stroustrup: like 1TBS, except that a continuation keyword after a closing } starts its own line at the indent of the }.
  • allman: like Stroustrup, and every opening { ending a line that has other code goes on its own line at the indent of its closing }.

Only the braces of bodies change: templates, packages, blocks, the cases of a match / catch and the enumerators of a for. The braces of an argument (xs.map { x => ... }), of a body after => and of a block standing as a statement stay where they are, and so does a brace with a comment next to it, a one-line { ... } and a } that does not start its line.

The pass parses the text: if it cannot, or if the result would not be equivalent to the input, the input is returned unchanged (safety net).

object DocCommentSpacingNormalizer

Blank-line-before-scaladoc normalisation, by blank-lines.before-scaladoc.

Blank-line-before-scaladoc normalisation, by blank-lines.before-scaladoc.

With always, a scaladoc (or javadoc) comment starting its own line has a blank line before it (with always-multiline, only a multi-line one), except at the start of the file and directly after a line that opens a block (see LineLayout.isOpener): there only a multiline scaladoc gets one, while a single-line /** ... */ stays glued to the opener (the edges of a container body follow blank-lines.body-edges). With never, the blank lines before a scaladoc that follows another line of code are removed, except after an opener or a package clause. With keep, nothing changes. Other comments never cause a blank line to be added or removed.

The pass is token-aware: a line that starts inside a multi-line string or comment is never a scaladoc start. If the text cannot be tokenised, the input is returned unchanged (safety net).

object FormatterOff

The regions of a file that dixtra leaves as the author wrote them: from a comment // dixtra: off to the next comment // dixtra: on, or to the end of the file. A marker is a line or a block comment holding only the marker, in any letter case and with any spaces: //DIXTRA:OFF and /* dixtra : on */ are markers too. The regions of a file that dixtra leaves as the author wrote them: from a comment // dixtra: off to the next comment // dixtra: on, or to the end of the file. A marker is a line or a block comment holding only the marker, in any letter case and with any spaces: //DIXTRA:OFF and /* dixtra : on */ are markers too. An off inside a region, or an on outside one, does nothing.

The file is formatted as a whole, then the text between the markers of each region is put back as it was written. The code around a region is formatted, so a change around it that cannot keep the region as written (for example the indentation of a whole package body) makes the output unsafe, and the file is left unchanged.

object ImportSpacingNormalizer

The blank lines between imports: always removed.

object MethodSpacingNormalizer

Blank-line-between-methods normalisation.

Blank-line-between-methods normalisation.

Ensures a single blank line precedes every method definition that directly follows another statement, so adjacent defs are always visually separated. given definitions and extension groups are methods too and are separated exactly like defs.

A method's decorations — the annotations, scaladoc, and comments on the lines directly above its def (multi-line scaladoc included) — form one group with it, so the blank line goes before the whole group, never between a decoration and the def. The blank line is inserted only when the line before the group is non-blank and is not an opener: a line ending with { or : (Scala 3 braceless object A:) or with with (given A: B with), an extension (...) header, or a line ending with = or => that opens a braceless body (so a local given or def at the top of a method body is not pushed down). The blank lines at the top of a body follow blank-lines.body-edges instead (see EdgeBlankLines).

One-line definitions (val, lazy val, var, def, given, type, a one-line declaration without a body included) at the same indent whose keywords are both in an alignment group follow the groups instead: two adjacent one-liners of the same group are a block and are not separated; between two of different groups the blank line follows BlankLinesConfig.betweenAlignmentGroups (kept as written, always, or never). Comments and annotations above a one-liner do not change that, but a scaladoc does: the blank line before a definition with a scaladoc follows blank-lines.before-scaladoc (added with always, and with always-multiline for a multi-line scaladoc), and a one-line one also gets a blank line after it, before the next statement at its indent.

This is a line pass keyed off lines whose first token (after optional modifiers, including qualified private[x] / protected[x]) is def, given, or extension, which is robust for the rendered output where signatures start their own line. It is token-aware: a line that starts inside a multi-line string or comment is never a method start, and no line is ever inserted inside such a token. If the text cannot be tokenised, the input is returned unchanged (safety net).

object Normalize

The text-normalisation pipeline applied after tree rendering.

The text-normalisation pipeline applied after tree rendering.

These passes operate on already-rendered text (not the AST) to enforce whole-file, cross-construct layout rules: placing braces by the brace indentation style, reflowing comments, canonicalising => spacing, separating adjacent methods, putting a blank line before scaladoc, and collapsing redundant blank-line runs. Redundant whitespace is collapsed before rendering instead (see WhitespaceNormalizer), so the alignment the renderers add is kept. Ordering matters — braces are placed first, then comments are reflowed and arrow spacing is enforced, then method and scaladoc separation insert blanks, blank-line runs are collapsed, and finally trailing comments are aligned — so the facade sequences them in one place. Every pass is token-aware and leaves the interior of string literals and comments untouched.

object TrailingCommentNormalizer

Trailing comments: the one-line comments at the end of a line of code.

Trailing comments: the one-line comments at the end of a line of code.

A trailing comment never counts in the width of its line, so the code before it never breaks because of it. Two passes change where it goes:

  • moveAbove, with overflow.trailing-comment = move-above: a line that goes past the maximum width with its trailing comment gets the comment on a line of its own above, at the indent of the line. When the line above is a // comment, an empty // line keeps the two comments apart, so that the comment reflow does not join them.
  • align, with alignment.trailing-comments: the trailing comments of consecutive lines start on one column, one space after the longest code. A line that would go past the maximum width once aligned stays as it is, and the lines before and after it align separately.

Both passes are token-aware; if the text cannot be tokenised, it is returned unchanged (safety net).

object WhitespaceNormalizer

Token-aware intra-line whitespace normalisation.

Token-aware intra-line whitespace normalisation.

Collapses runs of horizontal whitespace between tokens on the same line to a single space, so val a = "3" becomes val a = "3". It runs on the source before it is parsed, and on the source slices the renderers copy, tokenising them with Scalameta:

  • String, interpolation, and comment contents are single tokens, never whitespace tokens, so their interior spacing is inherently preserved.
  • Leading (indentation) whitespace is preserved, but for a tab, which becomes two spaces: indentation mixing tabs and spaces, as the renderers would write next to it, is not valid Scala 3.
  • Newlines and blank lines are preserved.

If the text cannot be tokenised, the input is returned unchanged (safety net).
